High 1 - [Verified] SQLCipher key can leak through macOS Keychain subprocess argv. File: whatsapp-bridge/keychain.go:134-165, especially keychain.go:157-161. Defect: the first-run macOS write calls security add-generic-password with -w <key>, which places the raw 64-hex DB key in the child process command line while it runs. Scenario: on first run, or after a proven missing key, another local process polls process arguments during key creation, captures the DB key, then decrypts both messages.db and session.db because db.go:64 and bridge.go:86 use the same key for both stores. Fix: replace the security CLI write with the native Keychain API, or another path that never carries the secret in argv; also keep the no-overwrite behavior currently implemented at keychain.go:153-162.

Medium 1 - [Verified] Media confirm claims the draft too late, so duplicate uploads and post-expiry sends are possible. File: whatsapp-bridge/sends.go:365-376, whatsapp-bridge/sends_media.go:297, whatsapp-bridge/sends.go:396-400, whatsapp-bridge/sends.go:296-300. Defect: for file/audio drafts, buildMediaMessage uploads bytes to WhatsApp before the UPDATE that atomically changes status from draft to confirmed, and that UPDATE does not re-check created_at against the one-hour TTL. Scenario: two callers with the bridge token confirm the same media draft at the same time; both upload the file, then only one wins the status update and sends, or one caller starts confirmation at second 3599, a slow upload takes minutes, and the draft is still confirmed and sent after expiry. Fix: claim the draft before upload with one atomic UPDATE or UPDATE ... RETURNING that requires status='draft' and created_at >= now - draftTTLSeconds, use a temporary confirming state, and define how to return to draft or failed if upload fails.

Medium 2 - [Verified] Outbound file_path size limits happen after reading the whole file into memory. File: whatsapp-bridge/sends_media.go:53-57, whatsapp-bridge/sends_media.go:133-140, whatsapp-bridge/sends_media.go:174-176. Defect: materializeOutboundFile runs os.ReadFile(clean) before checkSizeLimit, so a huge file under an allowed send root can exhaust memory before the size error is returned. Scenario: a token-holding caller asks to draft-send a 5 GB file from Downloads; the bridge allocates the whole file and can crash before it reaches the 100 MiB document cap or 16 MiB image/audio cap. Fix: reject by os.Stat size before full read, read only the first bytes needed for MIME sniffing, then stream-copy through an io.LimitedReader into the outbound file.

Medium 3 - [Verified] Inbound media download has no bridge-side max size before memory and disk write. File: whatsapp-bridge/media_download.go:152-156, whatsapp-bridge/media_download.go:190-200. Defect: DownloadMedia reads bytes from whatsmeow.Client.Download and writes them with os.WriteFile without comparing media_file_length or the returned byte count to a local cap. Scenario: a malformed stored row or unexpected WhatsApp media response returns far more bytes than normal; the bridge holds those bytes in memory and writes them to disk under MediaPath. Fix: reject rows whose media_file_length is above a configured cap, enforce a hard cap on len(bytes) after Download, and use separate caps per media type.

Medium 4 - [Verified] audit.log stores phone-number JIDs and user search terms. File: whatsapp-mcp-server/main.py:154-171, whatsapp-mcp-server/main.py:498-502, whatsapp-mcp-server/main.py:714-715, whatsapp-mcp-server/main.py:745-746, whatsapp-mcp-server/main.py:807-809, whatsapp-mcp-server/main.py:832-833; live evidence: audit.log:4-7 has phone-number JIDs after redaction in my terminal output. Defect: _audit says it redacts nothing and the tools pass recipient_jid, chat_jid, target message IDs, search q, draft IDs, result summaries, and error text into a 0600 JSONL log. Scenario: if audit.log is copied into a support bundle, backup, or weaker-permission folder, it exposes contacted phone numbers and search terms; I verified normal send audit uses text_len rather than message text. Fix: redact or hash JIDs and phone-like digit runs by default, keep only last four digits for operator use, and store full raw identifiers only in the encrypted DB if they are needed.

Medium 5 - [Verified] The prompt-injection scrubber is exact-phrase only and has documented bypasses. File: whatsapp-bridge/scrubber.go:12-31, whatsapp-bridge/scrubber.go:56-62, whatsapp-bridge/scrubber_test.go:178-218, whatsapp-mcp-server/tests/test_scrub.py:241-283. Defect: the scrubber strips only fixed case-insensitive substrings, while tests explicitly skip Unicode homoglyphs, added whitespace, embedded delimiters, base64, RTL override, zero-width joiners, indirect URL preview text, tool spoofing, and exfiltration phrasing. Scenario: a WhatsApp message such as ignore<zero-width joiner>previous<zero-width joiner>instructions or a tool-spoof instruction reaches Claude through list_messages without a scrub flag. Fix: normalize Unicode, remove zero-width and RTL controls, collapse whitespace and separators, add tool-name/exfiltration detectors, and promote these skipped cases into blocking tests.

Low 1 - [Verified] Existing bridge token file permissions are not checked. File: whatsapp-bridge/auth_token.go:34-40, whatsapp-bridge/auth_token.go:50-54; current live file store/bridge.token is 0600, and .gitignore:72 ignores the default token file. Defect: loadOrMintBridgeToken creates a new token as 0600, but if a token file already exists it accepts the value without checking owner, mode, hard links, or symlinks. Scenario: an older install or manual copy leaves bridge.token mode 0644; another local user reads it and can call admin and send endpoints. Fix: os.Lstat/os.Stat the existing token file, require regular file, expected owner, and no group/other bits, chmod or refuse on mismatch, and use O_NOFOLLOW plus O_CREATE|O_EXCL for new files where supported.

Low 2 - [Verified] JSON body parsing is not strict and the size cap is a soft LimitReader cap. File: whatsapp-bridge/server.go:110, whatsapp-bridge/server.go:491, whatsapp-bridge/sends.go:77, whatsapp-bridge/media_download.go:378, whatsapp-bridge/presence.go:29, whatsapp-bridge/presence.go:68, whatsapp-bridge/presence.go:112. Defect: handlers call json.NewDecoder(io.LimitReader(...)).Decode once, with no http.MaxBytesReader, no DisallowUnknownFields, and no second EOF check. Scenario: a body like {"online":true}{"online":false} is accepted as the first JSON value, unknown fields are silently ignored, and a body that is valid before the LimitReader boundary can be accepted while trailing bytes are not treated as a 413. Fix: add a shared decodeJSON(w,r,max,&dst) helper using http.MaxBytesReader, DisallowUnknownFields, a second Decode expecting io.EOF, and a clear 413 for oversized bodies.

Low 3 - [Verified] Contact search uses bind parameters, but LIKE wildcards from the user are not escaped. File: whatsapp-bridge/server.go:723-754. Defect: q is parameterized, so I did not find SQL injection, but '%' and '_' keep their SQLite wildcard meaning in normalized_name LIKE ?, normalized_full_name LIKE ?, phone LIKE ?, and lid LIKE ?. Scenario: q=% returns up to the 100 most recently updated contacts rather than searching for a literal percent sign. Fix: escape %, _, and the escape byte in user input and add LIKE ? ESCAPE '\\'.

Low 4 - [Verified] .env secret hygiene depends on file permissions but the loader does not enforce them. File: whatsapp-bridge/env_file.go:27-39, whatsapp-bridge/env_file.go:55-91, .env.example:20-27, .gitignore:11-14. Defect: loadDotEnv will load WHATSAPP_DB_KEY or WHATSAPP_WHISPER_API_KEY from any found .env without checking whether the file is group/world-readable; current .env is 0600 and I redacted its values while reading. Scenario: a user copies .env.example to .env under a permissive umask and adds WHATSAPP_DB_KEY; the bridge loads a secret from a file another local user can read. Fix: when a .env contains keys matching KEY/TOKEN/SECRET/PASSWORD, refuse or warn if group/other bits are set, and document chmod 600.
